**New initiative, 2026-09-13: a GitHub Actions–based "has the underlying law changed since we last verified it" watcher, planned with Claude CLI, starting with a Colorado proof of concept before building anything.** Taylor wants this built eventually but explicitly not yet — the immediate ask was to start gathering the groundwork data now (per-clause statute citations) so the actual workflow build is easy later, rather than deferring data collection until the workflow itself is built. Key decisions made in planning: citations live in **new, per-state files** (`lease-clause-citations-CO.csv`, one per state as each gets built), not packed into the existing `lease-clauses.csv` and not one shared cross-state file, because (a) a shared multi-state clause needs one citation per state it's tagged with, which doesn't fit cleanly into one `lease-clauses.csv` cell, (b) Taylor didn't want the already-large main CSV to grow further, and (c) the actual consumer is a **per-state scheduled workflow** (the original ask was explicitly "one workflow per state"), which maps 1:1 onto one file per state and needs zero cross-state awareness — a shared clause just gets its own independent row in every state's file that tags it, and stitching those together into a cross-state view (if ever wanted) is an occasional manual/Claude-CLI job, not something the per-state files or workflows need to do themselves. (Claude CLI's first instinct was one consolidated cross-state file with a `state` column — reconsidered after Taylor pushed on it, since that design optimizes for a cross-state analysis view nobody had actually asked for, at the cost of the 1:1 workflow mapping that was the whole point.) The bigger, more invasive fix to `lease-clauses.csv` itself — unpivoting it to one row per clause-*per-state*, which would also fix the pre-existing `effective_from`/`last_checked` per-row-not-per-state limitation — remains the long-term answer if the per-state-citations-file approach ever starts to strain, but is not needed for this. Change-detection will likely combine the free LegiScan bill-tracking API (30,000 queries/month, full-text search across all state bills) for statutory changes with a small targeted direct-check for the administrative/regulatory/model-code citations LegiScan structurally cannot see (already-encountered real examples: the CFR 36.104 "version trap," North Dakota's incorporated International Fire Code) — covering each source's real gap rather than building two redundant systems. Notifications are plain email to Taylor for the POC.

- [Aug 2026] — **Property archiving is a live flag (`archived`/`archivedAt`/`archivedReason`), never a snapshot, and its cascading hide of tenants/leases/maintenance is computed via a query-time join, never a stored/copied flag on those child records.** Taylor's explicit requirement after asking "does archiving create a snapshot?" — nothing about a Tenant/Lease/etc. is touched, copied, or modified when its property is archived; list queries just filter on `property.archived` at read time. Reason this matters: unarchiving a property must instantly restore full visibility everywhere (Tenants page, Leases page, Maintenance hub, Dashboard) with zero data to reconcile, which only works if nothing was ever duplicated or flagged on the child rows themselves. Keep this pattern for any future domain that needs the same "hidden while the parent is archived" behavior — filter the list query, don't propagate a flag.
- [Aug 2026] — ~~Deleting a Tenant/Lease/Income/Expense/MaintenanceRequest/MaintenanceSchedule is blocked while its property is archived.~~ **Rejected same day it was built — Taylor's explicit call: "blocking is not what I wanted."** Replaced with real soft-delete (`deleted`/`deletedAt` on all 6, `DELETE` sets them instead of removing the row, `POST /:id/restore` clears them) — see the What's been built entry for the full shape. The underlying instinct that led to the blocking attempt (don't let "who rented it, what it earned, maintenance done" history get destroyed — memory `project_property_archiving_not_delete`) was correct; the *mechanism* was wrong. Do not reintroduce delete-blocking for these 6 models — hide-not-destroy is the settled pattern now. Property Specs (the 7 categories) are deliberately the one exception: they keep plain hard-delete, since they already have their own retire/replace soft-lifecycle and weren't in Taylor's stated soft-delete scope.
- [Aug 2026] — **A soft-deleted record's `DELETE` is idempotent (calling it twice just re-confirms 204), but `POST /:id/restore` is not (400 if the record isn't currently deleted).** Deliberate asymmetry: `DELETE` follows normal HTTP idempotency semantics for the same action repeated; `restore` is a real state-transition action (like Property's archive/unarchive, which have the same non-idempotent shape) where calling it on a record that's already in the target state signals a genuine logic error worth surfacing, not a harmless no-op.
- [Aug 2026] — **Reassigning a tenant to a different property is "copy details, don't move" — a new Tenant row (`previousTenantId` pointing back to the old one), never a literal reassignment of the existing row's `propertyId`.** Considered and rejected: just changing `Tenant.propertyId` on the existing record. That would break the standing rule that a Tenant record represents "applied to this specific property" (CLAUDE.md's own decisions log, the "No separate Applicant model" entry) and would silently rewrite what that field has meant everywhere else in the app. The copy-and-link approach costs a little re-entry (mitigated by the "Copy details from an existing tenant" picker pre-filling name/phone/email) but keeps every existing assumption about `Tenant.propertyId` true, and gives a genuinely fresh application (`applicationStatus` back to PENDING, screening fields blank) for the new property — which is actually correct, since those should be reassessed for a new tenancy, not carried over stale.
- [Aug 2026] — **`?deleted=all` means "show me literally everyone" — it bypasses both the deleted filter and the archived-property cascading hide, on every list endpoint that has one (Tenant, Lease, MaintenanceRequest, MaintenanceSchedule).** Caught as a real bug in review: the first implementation only made `all` ignore the `deleted` flag, so a tenant at an archived property still silently disappeared from the "copy from an existing tenant" picker — the exact case (a tenant moving off a just-archived property) the picker exists for. `all` is now defined as a full bypass of every hiding mechanism at once, not just one of them; keep that definition for any future `?deleted=` consumer.
- [Aug 2026] — **`Property`'s Delete button is only ever shown when the property has zero dependents (`canDelete`, computed server-side and returned from GET/PUT/archive/unarchive).** Taylor's call after noticing Delete was still offered on properties where it could never actually succeed (it already 400'd with "archive it instead" once anything was attached) — better to not present a dead-end option at all than to let a landlord discover it's blocked after clicking. Once anything real is attached, Archive is the only removal-adjacent action shown; this doesn't change `DELETE /api/properties/:id`'s own backend behavior, only whether the frontend offers the button.
- [Aug 2026] — **Each state's clause verification pass gets its own decision log file (`lease-clause-decision-log-<STATE>.md`), never one continuously-growing document.** Established when Wyoming (state #2) closed out — Taylor's explicit call, recorded in the WY log's own handoff section. `lease-clause-decision-log-CO.md` stays as state #1's record and as the methodology reference every future state's log should open by pointing back to; each new log only needs to record what's specific to that state (statute findings, clause decisions, process learnings), not restate the shared methodology. Do not fold future states' research back into the CO file.
- [Aug 2026] — **A clause earning a second state tag (e.g. `states: ["CO", "WY"]`) requires the same primary-source rigor as earning the first one — two states independently agreeing a clause is generic is not treated as proof the clause is universal.** Confirmed explicitly in the WY decision log (§7): even after a clause was cross-checked clean against both CO and WY law, it stayed tagged `["CO", "WY"]` rather than being promoted to blank/universal. "Universal" remains an earned status requiring all 50 states individually verified, per the original Aug 2026 `states`-semantics rework — two states is progress toward that, not a shortcut past it.
- [Aug 2026] — **A source's reliability does not transfer from state to state — re-check even a previously-trusted domain's claims against the new state's primary sources.** Surfaced during the WY pass: Hemlane was caught making three separate fabricated/wrong claims about Wyoming law in this project alone (a false 2023 deposit-interest-account amendment, a nonexistent "Mobile Home Parks Act," a fictional DV-related deposit provision), and a second domain (LeaseWisely) fabricated a list of ~15 "required" Wyoming disclosures with no statute backing any of them. Extends the standing "verify against a primary source, never trust a secondary site even when several agree" rule (established during the original Colorado guest-policy episode) with a sharper corollary: don't let a domain's track record in one state's research earn it a pass in the next state's.
- [Aug 2026] — **When two clause variants reflect a genuine legal-strategy *posture* choice (not competing facts about what the law says), ship one curated answer and preserve the other as `is_active: FALSE`, not delete it.** Established during WY's Safe Homes Act clause, where a statutorily-accurate defense-framed version and a more aggressive proactive-termination-right version both existed as real options; Taylor picked the defense-framed one to ship. Matches the rest of the library being one curated answer per topic rather than a landlord-facing menu of legal strategies — building an actual "let the landlord pick their posture" UI is a real, separate product-scope decision, not something that falls out of the content work for free. The unselected variant stays in the CSV/decision log, ready to ship if that feature is ever built.
- [Aug 2026] — **Any script that compiles the clause-library CSV into `clauseTemplates.js` must filter rows on both `is_active === "TRUE"` AND `content_type === "LEASE_CLAUSE"` — filtering on `is_active` alone is not sufficient once the CSV holds more than one content type.** The original CO-pass generator script only checked `is_active`, which happened to work by accident because the CO CSV's LANDLORD_EDUCATION rows were added in a separate, later pass than the one that generated `clauseTemplates.js`. Reusing that same script unmodified against the combined CO+WY CSV (which has both content types present from the start) would have leaked all 52 active `LANDLORD_EDUCATION` rows into `clauseTemplates.js` as fake lease clauses — caught via a count sanity-check before shipping, not by inspection. Any future regeneration of these files must filter on `content_type` explicitly; don't assume a script that worked once still encodes the right filter.

- [2026-09-13] — **When a state's decision-log narrative and the clause-library CSV disagree, the CSV is treated as fact — established as a standing rule in the architecture-review log's Addendum L §L.3 ("a log entry is not a library change"), adopted here for how this app consumes both.** Concretely: this session regenerated `clauseTemplates.js`/`clauseResearchMetadata.js`/`landlordEducation.js` directly from `lease-clauses.csv` without hand-reconciling every state's prose decision log first, on the reasoning that the CSV is what the architecture-review log itself says is authoritative (it records at least one real case — North Dakota — where a state's log claimed a clause existed and the CSV never actually had it). Any future clause-library sync should follow the same rule: trust the CSV, use the logs for the "why."
- [2026-09-13] — **`Clause.group` (and `clauseTemplates.js`'s shipped groups) stay a closed, app-owned taxonomy — a CSV row using a group name outside `CLAUSE_GROUPS` gets remapped to the closest existing group at generation time, not used to silently grow the taxonomy.** Surfaced when the KS–SD research batch introduced 4 Minnesota rows tagged with one-off groups ("Insurance & Liability," "Parking," "Storage," "Rent & Fees") that don't exist in `backend/src/lib/clauseGroups.js`. Reason: `Clause.group` is validated against that fixed list elsewhere in the app (numbering in `leaseClauseOrdering.js`, a route test asserting every shipped template's group is a member of it), and the whole reason `CLAUSE_GROUPS` is a plain array instead of a Prisma enum is so *Taylor* can rename/reorder it deliberately — not so an external research pass's incidental categorization choices flow in unreviewed. The remap table lives inline in the (uncommitted, one-off) generator script; if a future state's research introduces more one-off groups, extend that same remap rather than expanding `CLAUSE_GROUPS` for a handful of rows.

- [2026-09-14] — **`lease-clause-citations-<STATE>.csv`'s `citation_status` vocabulary is extended per state to fit that state's actual evidentiary shape, rather than forcing every state through CO's original four values (`CITED`/`GENERIC`/`NOT_STATUTE`/`REMOVED`).** WY's citation file introduces two new values CO never needed: `CONFIRMED_ABSENT` (a real "no such WY statute/right exists" finding whose evidentiary basis is secondary-source agreement rather than a specific primary section actually read for that exact question) and reuses `NOT_STATUTE` for one row (carbon-monoxide detector rules, which are IRC/local-building-code matters, not a landlord-tenant statute at all). Reason this wasn't just forced into `GENERIC`/`CITED`: Wyoming's own research methodology treats a confirmed absence as equally load-bearing as a confirmed presence (established during the WY clause-library pass — see the Aug 2026 decisions log entries on proof-of-absence), so its citation file needed a status that says "we know the answer is no, backed by real evidence" as clearly as `CITED` says "we know the answer is yes, backed by a specific section." Where a WY absence finding *did* rest on an actual primary-source full-text read of a specific section (e.g. `edu-no-deposit-cap-interest-account-wy`, confirmed absent by reading all of §§1-21-1207–1211 directly), it's `CITED` with that section as the citation, not `CONFIRMED_ABSENT` — the new status is reserved for absence findings whose only basis is secondary-source agreement. Each future state's citation file should do the same: start from CO's vocabulary, add a new value only when a state's research genuinely produces a category CO's four didn't need, and document why in this log rather than silently reusing a value for something it wasn't defined to mean.

- [2026-09-14] — **LegiScan's `getSearch` always needs `year=1` (all years) — its default scope is the current legislative session only, which structurally cannot find a historical bill.** Confirmed empirically, not assumed: this project's own two named validation cases (searching "38-12-105" for SB21-173, "38-12-103" for HB25-1249) both returned 0 hits under the default scope and both resolved correctly at 99-100% relevance under `year=1`. This is now permanent in `legiscanSearch` for every jurisdiction it's called against (CO sections and the federal-statute-via-Congress check both go through the same function). Do not remove `year=1` to "reduce noise" — the existing relevance filter (≥50) and per-section seen-bill dedup already control noise; narrowing the year scope would just reintroduce the exact blind spot this entry documents.
- [2026-09-14] — **Any state's legal-watch workflow needs a `--seed-baseline` run before its first real `check` run, every time.** A real check treats "not in the state file's seen-bill list" as "new, worth emailing about" — correct once a baseline exists, wrong on a state's very first run, when the state file starts empty and every already-known historical bill would look new. `--seed-baseline` runs the identical live query/write-state logic as a real check but never emails, specifically to establish that starting point first. This isn't CO-specific plumbing — any future state's workflow (WY, KS, NE, MN, ND, SD) needs the same one-time step before its schedule is trusted to run unattended, and should follow the same command name/pattern rather than reinventing it per state.
- [2026-09-14] — **Never trust a GitHub Actions step's own reported "success" as proof that a `git push` inside it actually reached the remote — verify by checking the remote directly.** The legal-watch workflow's commit step reported success on its very first real run, its own log showed a real commit hash, and yet nothing ever reached `origin/main` — the two-line `git diff --cached --quiet || git commit ...` / `git diff --cached --quiet || git push` pattern silently no-ops the second line, because by then the commit already cleared the staged diff the second check is looking at. Caught only by pulling `main` locally and finding the commit missing, not by reading the run's status. Any future CI step that commits-then-pushes in two separately-gated lines should be treated as suspect; use one conditional block instead (see `legal-watch-co.yml`'s fixed version). This is also a standing instruction for how to validate any future automation in this repo: a green checkmark on a workflow run is not proof its side effects (a push, an email, a write to an external system) actually happened — check the actual downstream state.

## Full feature set (v2 and beyond)

### Lease builder (v2)
- Build a lease from scratch inside the app using a clause library
- Clause library: store verbatim lease language per clause, tagged by section number
- Mark clauses as violated and link to legal actions
- Violation builder: select clause → describe what happened → generate court-ready summary
- Key lesson (Taylor): magistrates want exact lease language, not summaries. Store verbatim.
- Key lesson (Taylor): early termination clause is critical — tenants abandoned lease and stopped paying rent. The lease only stated the term, not an explicit early termination penalty. App should flag if a lease is missing this clause.
- Template library: common clauses pre-populated, landlord edits to match their lease

### Legal tracker (v2)
- State-specific notice periods and delivery rules (all 50 US states)
- Action types: demand for payment, cure or quit, eviction complaint, summons, certified mail, court hearing, judgment, writ of restitution
- Full chronological timeline per case — date, delivery method, document attached
- Deadline calculator based on state rules
- State dropdown updates rules dynamically
- Links to lease clauses violated (from clause library)
- Court summary generator — clause text + violation description + evidence checklist

### Move-in / Move-out inspections (v2)
- Organized by room
- Per-room: photo/video uploads, condition ratings (Good / Fair / Poor) per item
- Move-out: damage notes with estimated repair cost per item
- Compare tab: side-by-side move-in vs move-out photo for every item that changed condition
- Signatures tab: tenant acknowledgment (email confirmation counts) with timestamp
- Deposit deduction letter generator: auto-generates the formal written notice to tenant
  itemizing damage deductions from deposit — required by Colorado law within 30 days of move-out

- Landlord policy: insurer, policy type, policy number, effective/expiration dates, named insured (LLC — pulls from Entity), agent contact, claims phone, annual premium, payment schedule

### Property specs (v2) — dual view (by room AND by category)

## Nationwide jurisdictional coverage plan (lease clauses + Legal Tracker)

> Captured Aug 2026 from outside research Taylor did with ChatGPT on how to scale both the
> Lease Builder clause library and the not-yet-built Legal Tracker to cover all 50 states (+
> municipalities) without re-researching everything from scratch per state. This is the one
> place this research is recorded — Taylor is not saving it anywhere else. See the decisions
> log entry (Aug 2026, "outside research from ChatGPT") for what was and wasn't adopted.

### The core model: jurisdiction as inherited layers, not a flat per-state matrix

Don't model "a Colorado lease" / "a Texas lease" / "a Denver lease" as separate documents, and
don't model eviction process as "one procedure per county." Both are actually a stack of layers,
where each layer only needs to store what it adds or overrides on top of the layer above it:

- **Lease content:** `Federal → State → Municipality → Property/tenancy type → Landlord preference`
  (e.g. Denver would store only what Denver adds on top of Colorado's baseline, not restate it).
- **Eviction process:** `State → judicial district/circuit → county/courthouse → municipality`,
  plus a property/tenancy-type branch (subsidized housing, mobile homes, tenancy-at-will, etc.,
  since those can add their own procedural branches regardless of location).

For lease content specifically, ChatGPT proposed classifying each rule as one of five types —
useful vocabulary even though we're not building a separate rules-database object for this
(see decisions log):
- `REQUIRED` — must be in the lease
- `CONDITIONAL` — required only if some property/tenancy fact is true (e.g. built pre-1978 →
  lead paint disclosure)
- `PROHIBITED` — lease cannot contain this provision at all
- `CONSTRAINED` — allowed, but only within a statutory limit (late fees, deposit caps, entry
  notice periods, etc.)
- `RECOMMENDED` — not legally required, but risk-management advisable (this is exactly Taylor's
  own early-termination lesson: not government-mandated, but materially affects enforceability)

**What we're actually doing with this**: our existing `Clause.states` (`String[]`) + `supersedes`
fields already cover the practical intent of REQUIRED/CONSTRAINED/supersede without a separate
rules table — a state-tagged clause *is* a CONSTRAINED or REQUIRED rule, a `supersedes` link *is*
the "this fully replaces the universal version" case. Keep using that mechanism for future clause
research passes. Do not build a formal decoupled rules-database layer, and do not build a
municipal-overlay layer, unless the app reaches real multi-municipality usage that actually needs
it — see the decisions log entry for why this was deferred rather than adopted outright.

### How to research it, state by state (same discipline already proven out)

This matches the primary-source-or-don't-ship discipline already established in
`project_state_law_research_aug2026` (the fabricated Colorado guest-policy episode) — ChatGPT's
research independently arrived at the same rule:

- **Canonical sources are government primary sources only**: each state's own legislature/code
  publisher for statutes, the state's judiciary for court rules/forms/procedure, and the
  municipality's own code for city overlays. Never a landlord-content site, even when several
  agree — that's a sign of copied content, not independent verification.
- **Cornell Legal Information Institute (Cornell LII)** — state law collection + landlord-tenant
  topic area — is a good *discovery/index* tool for finding where a state's law lives, but treat
  it as a pointer only; always trace through to the actual primary source it names.
- Some states publish their own curated landlord-tenant guides, which are a great starting index
  (someone in the legislature already did partial research for you) — Colorado's Legislative
  Council publishes "Laws Regulating Landlords and Tenants" covering residential leases, federal
  law interplay, and examples of stricter local law. Look for the equivalent in each new state.
- Useful search patterns per state: `site:[state legislature domain] landlord tenant`,
  `site:[state court domain] eviction`, `site:[state court domain] landlord tenant forms`,
  `"[state] residential landlord tenant act"`, `"[state] required lease disclosures"`,
  `"[state] eviction court forms"`.
- **Build a "source registry" before researching individual rules**: one row per state naming
  where its statutes, courts, eviction guide, forms, and municipal-code portal live. Do this once
  per state as the first step of any future research pass — it turns "research this state's law"
  into a repeatable pipeline instead of starting from zero each time.
- No single database (commercial or government) covers this nationally — don't adopt a licensed
  commercial dataset as the canonical source (licensing/redistribution/update-guarantee/vendor-
  lock risk). Keep building our own normalized, primary-source-cited data on top of government
  sources, the same way `clauseTemplates.js` already does.
- Municipal overlays are the hardest layer (no national repository of municipal codes) — when
  they're ever tackled, do it selectively for cities with real, substantial landlord-tenant
  ordinances (Denver, Boulder, NYC, Chicago, LA, etc. were the examples raised), not
  exhaustively across ~19,000 incorporated places. Several real candidates were already
  identified and explicitly dropped for this exact reason — see
  `project_state_law_research_aug2026`'s "explicitly dropped" list (NYC's bed bug disclosure
  ordinance, Chicago's local deposit cap) for what's waiting once a city-level tagging mechanism
  exists.
- A future idea, explicitly not being built now: an AI pipeline that periodically re-checks state
  legislature/judiciary/municipal sources for changes and flags a suggested diff for a human to
  review — never auto-applies a change to a live legal rule. Revisit only as a v3+ idea if the
  clause library's maintenance burden ever actually becomes a problem at the current manual pace.

### Rollout order

1. **Lease clauses**: continue expanding via the existing lightweight tagging model (no
   architecture change). Next batch is the "explicitly dropped" list in
   `project_state_law_research_aug2026` — those already have partial research done, just need

2. **Legal Tracker**: build Colorado-only first (matches the existing v2 roadmap ordering —
   `project_v2_roadmap_priority` — where Legal Tracker is deliberately last due to legal-accuracy

3. **Eviction-rule field sketch** (from ChatGPT, not yet a committed schema — a starting point

### Ownership hierarchy
```
User (Taylor)
  └── Entity (Steinbaugh Estates LLC — or "Self / Personal")
        └── Property (123 Maple St, Frederick CO)
```

### Entity / LLC
- Every property is owned by an Entity
- Entity can be "Self / Personal" for landlords without an LLC — this is valid and common
- Entity is editable — landlords often buy personally then transfer to an LLC later
- Fields: legalName, entityType (LLC / S-Corp / Personal / Other), stateOfFormation,
  ein (encrypted), registeredAgent, formationDate, annualReportDueDate (reminder 60 days out),
  bankAccount (which account rent flows into)
- annualReportDueDate reminder is important — missing this can dissolve the LLC and wipe out liability protection
- Named insured on insurance policy pulls from Entity, not from User
- Landlord name on lease is the Entity name, not the user's personal name
- Current entities (Taylor): Steinbaugh Estates LLC → 123 Maple St, Frederick CO

### Multi-property / multi-landlord
- Every record has a `propertyId`
- Every record has an `entityId` (which entity/LLC owns the property)
- Every record has a `userId` (ultimate owner — for dashboard access across all entities)
- Dashboard shows all properties across all entities for the logged-in user

### Tenants
- Multiple tenants per lease (married couple, roommates, guarantors)
- Roles: Primary (main contact, signs first), Co-tenant, Guarantor (legally responsible, not an occupant)

- Fields: name, phone, email, date of birth, ID verified, credit check status/date, employment
- Emergency contact per tenant
- Rent is always due in full — do NOT track individual payment splits between tenants
  If rent is late, ALL tenants are late regardless of who paid what

## Taylor's real-world lessons
> These are lessons from Taylor's actual landlord experience — not generic tips.
> Each one shaped a specific feature. Do not add to this list without Taylor's input.

1. **Lease clause visibility in court** — in a hearing, Taylor couldn't quickly show the magistrate which exact clause the tenant broke, or the verbatim language. The clause library in v2 exists specifically because of this. Magistrates want the exact words, not a summary.

2. **Early termination** — tenants abandoned the lease mid-term and stopped paying rent. The lease stated the term dates but had no explicit early termination penalty clause. Taylor has since added one. The app should flag leases missing an early termination clause.

3. **Move-in documentation** — photograph and video everything before handing keys. Get tenant acknowledgment in writing (email reply counts). Side-by-side comparison at move-out is your deposit dispute defense.

4. **Touch-up paint storage** — always note where leftover paint is stored (e.g. "labeled quart, garage shelf"). Critical at tenant turnover when you need to touch up walls.

5. **Spare flooring** — keep 2-3 spare boxes of each floor type. If a floor gets damaged and the product is discontinued, you'll need those spares. Flag when spare stock hits zero.

## Competitive research: Manora

> Discovered while brainstorming names with Claude Desktop. Not a landlord lesson from Taylor —
> external research to inform the Maintenance module's design when it's built.

Manora (manora.io) is an early-access, maintenance-only app for landlords — no rent, leases, or accounting. Core flow: tenant reports an issue via a unique link (no login/app required) → landlord classifies urgency/category and assigns a contractor → contractor gets a dedicated portal (invite-only, no account needed) to accept, upload photos, log costs → landlord reviews and closes. Every property automatically builds a searchable maintenance history.

Design choices worth incorporating into our maintenance module:
- **Property-centric history, not task-centric** — repairs, visits, and photos roll up into a permanent per-property timeline. Build the data model around "property → full history," not "list of requests."
- **Zero-friction entry points** — tenants and contractors interact via unique, revocable links with no account required.
- **Role-based access separation** — landlord/property manager, contractor, and tenant each see only their own scoped view; contractor sees only assigned jobs; tenant links are per-property and revocable.
- **Full audit trail as a selling point** — every status change is timestamped and attributed, surfaced to the user, not just logged internally.
- **Sharp problem framing in positioning** — built around a concrete pain point ("repairs coordinated over WhatsApp get lost"), not generic "manage your properties" messaging.
- **Reporting layer** — cost per property/contractor, average resolution time, portfolio-level view.

**Differentiation angle:** Manora doesn't do rent, leases, or accounting — so "everything Manora does for maintenance, plus the rest of property management" is a clean positioning story once our maintenance module is built.

## AI integration plan

### Philosophy
AI earns its place when it saves the landlord real time or catches something they'd otherwise miss.
It's gimmicky when it summarizes things the landlord already knows or answers questions Google could answer faster.
**AI should make the landlord feel like they have a knowledgeable friend in their pocket — not a chatbot.**

### Hard rules
- Never give legal *advice* — only legal *information*. "Colorado law requires 10 days notice" is fine. "You'll win this case" is not.
- Never make tenant screening recommendations — Fair Housing Act liability risk. Avoid entirely.
- Never predict rent prices — dedicated tools do this better. Integrate with Rentometer/Zillow if needed, don't compete.
- Always make AI output reviewable and editable before it's sent or saved — the landlord is always in control.
- AI is a suggestion engine, not an autopilot.

### How it works technically
- Use the Anthropic API (Claude) — same model Taylor is talking to right now
- Backend calls the API with relevant context (state, tenant name, amount owed, etc.)
- Response streams back into the UI
- Cost: cents per call — absorb into subscription price or add a small AI usage tier in v3+
- Model to use: claude-sonnet-4-6 (fast, cost-effective for in-app features)

### Roadmap

#### v1 — No AI
Get the core app solid first. AI on a broken foundation is expensive noise.

#### v2 — Two features that clearly earn their place

**1. Legal notice drafter**
Highest value AI feature in the entire app. Legal language is intimidating, state-specific, and time-sensitive.
- Landlord selects: state, notice type, tenant name, amount owed, days late
- AI generates the correct notice with proper statutory language for that state
- Landlord reviews and edits before printing/sending
- Also: plain-English translation of court documents — landlord pastes in a document, AI explains what it means
- Warning system: "You served a 3-day notice but Colorado requires 10 days for non-payment — this may not hold up in court"

**2. Maintenance triage**
Tenant submits a request in plain language ("water coming out from under the sink").
AI reads it and surfaces:
- Likely cause
- Urgency level (low / medium / high / emergency)
- Suggested vendor type (plumber, electrician, HVAC, general handyman)
- Estimated cost range
Saves the landlord a Google search and helps them prioritize the queue.

#### v3 — Expanded AI features

**Lease clause reviewer**
When building a lease (v2 feature), AI reviews the draft and flags:
- Missing clauses based on state requirements
- Missing clauses based on Taylor's own lesson learned (e.g. no early termination clause)
- Clauses that may exceed state statutory limits (e.g. late fees)
- Suggests additions based on property type

**Inspection photo comparison**
- Landlord uploads move-out photo alongside the stored move-in photo
- AI flags potential damage differences
- Draft deposit deduction letter automatically from damage notes already in the system

**Expense categorization & tax flagging**
- Flag likely Schedule E deductions the landlord may be missing
- Flag unusual expense spikes: "Repairs this month are 3x your average — want to review?"
- Year-end summary formatted for accountant handoff

**Smart data entry (property specs)**
- Landlord types "painted kitchen with Sherwin-Williams Agreeable Gray eggshell" → AI parses into correct fields
- Photo of paint can label or appliance data plate → AI reads it and populates the record
- Reduces friction for filling out property specs

### Features to never build with AI
- General "chat with your property" chatbot — sounds cool, rarely used after week one
- Tenant approval recommendations — Fair Housing Act risk
- Rent price predictions — better tools exist for this
- Anything that sends to a tenant without landlord review first
